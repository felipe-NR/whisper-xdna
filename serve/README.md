# Serving it

`npu_stt_server.py` wraps the encoder in an HTTP endpoint that speaks the same
multipart contract as `whisper.cpp`'s `/inference`, so an existing client can be
pointed at it without changes:

```
POST /inference
  file            audio (wav / webm / ogg)
  response_format json
  audio_ctx       encoder positions to compute (see below)
  language        e.g. ru
→ {"text": "..."}
```

The pipeline inside is: audio → mel → **encoder on the NPU** → decoder on the
CPU, both halves out of the checkpoint `NPU_STT_MODEL` names (`large-v3-turbo`
by default).

**Both halves have to come from the same checkpoint.** Feeding the
`large-v3-turbo` encoder's output to a `large-v3` decoder produces garbage while
the cosine stays unchanged — the failure is a silently wrong transcription, not
an error. Taking the weights out of the loaded model rather than a separate
`.npz` is what makes that mismatch unrepresentable; `NPU_STT_WEIGHTS` is the one
way back into it, so an `.npz` there must match the model you name.

`tiny`, `small`, `large-v3` and `large-v3-turbo` have all been run end to end
through this path; the mel bin count follows the checkpoint, so 80-mel and
128-mel models both work.

## Starting it

```bash
RENDER_GID=$(getent group render | cut -d: -f3) WITH_REFERENCE=1 \
  docker compose up -d stt
```

The first start downloads the `large-v3-turbo` checkpoint (~1.6 GB), lifts the
encoder half out of it as fp32 and uploads it to the device; the torch encoder
is dropped before the decoder ever runs, so the 635M parameters that would
never execute are not kept. Then it compiles an overlay set per context on the
ladder, which is minutes cold and seconds after. Both caches live in named
volumes, so a container restart pays neither again.

Nothing has to be generated by hand. `NPU_STT_WEIGHTS` still accepts an `.npz`
from `tools/dump_ref.py --model large-v3-turbo` if the machine cannot reach
the internet.

## Two details that cost a day to find

**One process, one venv.** The encoder needs numpy, `ml_dtypes` and `pyxrt`; the
mel and the decoder need torch and `openai-whisper`. Rather than two processes
and a socket, both live in the torch venv — `rawxrt` only shells out to IRON for
compilation, which is a subprocess anyway. Verify this on your own setup rather
than assuming: under the serving interpreter the acceptance suite must still
give the same bit-identical result.

**Changing `audio_ctx` between requests will kill the NPU path** if you do not
unload the old geometry first: `DRM_IOCTL_AMDXDNA_CREATE_HWCTX IOCTL failed
(err=-22)`, after which the internal flags stay off for the life of the process
and everything runs on the host path (3.3 s → 18.3 s). Unloading costs ~500 ms
on the first request after a switch.

The subtle part: the unload must drop the scratch buffers *and* their views
along with the contexts. Sub-BOs carved out of an fc2 design's `A` buffer
survive the context going away, the next pass allocates a new one, and fc1 then
writes into nothing — **timings stay normal and the text comes back silently
wrong** (English output for Russian speech). A speed benchmark does not see
this. Only comparing the output does.

## `audio_ctx` matters more than you would think

Whisper always pads its input to a 30 s window = 1500 encoder positions, but you
can compute fewer. On this hardware, against `whisper.cpp` on the same machine:

| `audio_ctx` | NPU encoder | whisper.cpp encode | speedup |
|---|---|---|---|
| 512 | 1582 ms | 2074 ms | 1.31x |
| 768 | 2267 ms | 3282 ms | 1.45x |
| 1024 | 2456 ms | 4377 ms | 1.79x |
| 1500 | 3346 ms | 6969 ms | 2.09x |

The wall-clock advantage shrinks toward short contexts; CPU occupancy does not
(0.25 of a core against 13–15 at every context). If your workload is short
utterances, the reason to use this is the *cores*, not the latency.

Clients should size `audio_ctx` to the actual speech length — but note that
truncating below the speech length makes Whisper's decoder loop on the tail
(1217 decode steps instead of 103 on a 22.6 s clip), so leave headroom.

## Falling back to a CPU implementation

Set `STT_CPU_URL` to a `whisper.cpp` `/inference` endpoint and the server will
route to it rather than fail or make the caller wait:

- **NPU path raised** — the request is proxied, the caller gets a normal `200`
  with correct text (~2.15 s), and the log carries the traceback plus
  `FALLBACK->CPU [error]`. Silent degradation is the thing to avoid here: a
  fallback nobody notices is how you end up shipping the slow path for weeks.
- **Audio would not decode** — also proxied, because the two ffmpeg builds do
  not fail on the same inputs; costs 29 ms to find out.
- **The device is busy** — the second concurrent request goes to the CPU
  immediately rather than queueing. `STT_BUSY_WAIT_MS` sets how long to wait for
  the device first; **0 measured best on the tail** (worst-of-pair 4.06 s → 2.70 s),
  while a long wait wins on the *median* (the winner of the pair gets 1.94 s,
  the best number in the table). Pick by which one your users feel.

Empty `STT_CPU_URL` (the default) disables all of this.

Two details worth copying: the proxy forwards the **original request bytes**, so
the CPU response is byte-identical to what the caller would have got hitting
that endpoint directly; and every response carries `X-STT-Path: npu|cpu`, with
counters (`served_npu`, `busy`, `error`, `decode`, `proxy_failed`) on `/health`,
so the fallback rate is visible instead of inferred.

Note the responses are *not* normalised between paths: `whisper.cpp` returns a
leading space and a trailing newline, this server does not. Clients that
`.strip()` will not notice; clients that do not, will.

Keep a fallback in the client too. Serving-side fallback covers a sick NPU; it
cannot cover the server process being dead.

## Long recordings

Whisper sees 30 s at a time, so anything longer is cut into windows and the
device runs them back to back under one lock. Measured on this machine, a
304 s clip at `audio_ctx=1500`:

| | |
|---|---|
| windows | 10 |
| encoder | 33.7 s (10 x ~3.4 s) |
| decoder | 5.6 s |
| mel | 22 ms |
| **wall clock** | **39.4 s** |

Two consequences worth knowing before pointing a client at it. The whole
request holds the device, so a second caller during those 39 s gets the CPU
fallback (or a 503 with no `STT_CPU_URL`). And 39 s is past the timeout most
clients give an HTTP request -- a 30 s client budget covers roughly 3.5 minutes
of speech, so long audio wants a longer timeout on the caller's side.

`NPU_STT_MAX_WINDOWS` (default 20, i.e. 10 minutes) truncates beyond that
rather than holding the device indefinitely; the response then carries
`X-STT-Truncated-S` with the number of seconds dropped, and the log says so.

## Decoder: torch or CTranslate2

The decoder runs on the CPU either way. `NPU_STT_DECODER` picks which one:

- `torch` (default): `whisper.decode` in fp32, as before.
- `ct2`: CTranslate2 in int8 (`serve/ct2_decoder.py`). Same text, a quarter of
  the bytes per weight on a load that is bound by memory bandwidth.

Measured on a Ryzen 7 8700G, `large-v3-turbo`, `pt`, the service's own
`X-NPU-*` headers, median of 3 warm requests:

| clip | `audio_ctx` | torch: decoder / total | ct2: decoder / total | CPU per request, torch → ct2 |
|---|---|---|---|---|
| 6 s | 512 | 599 / 1767 ms | **142 / 1331 ms** | 1.35 → 1.21 s |
| 20 s | 1280 | 1414 / 4487 ms | **365 / 3454 ms** | 3.47 → 2.95 s |

The transcripts were identical on every request. `tests/test_ct2_decoder.py`
checks that on CPU against `whisper.decode` for 3 clips × 3 contexts, including
two where both decoders loop, and stop on the same token.

```bash
# compose.ct2.yml builds stt from Dockerfile with WITH_REFERENCE=1 WITH_CT2=1
# and sets NPU_STT_DECODER=ct2
RENDER_GID=$(getent group render | cut -d: -f3) VCS_REF=$(git rev-parse HEAD) \
  docker compose -f compose.yml -f compose.ct2.yml up -d --build stt
```

To make that the default for every `docker compose` call in the checkout, put
`COMPOSE_FILE=compose.yml:compose.ct2.yml` in `.env`. The build is the full
`Dockerfile` (measured: 202 s from nothing with `--no-cache` on a Ryzen 7
8700G, base images already pulled). `VCS_REF` becomes the image's
`org.opencontainers.image.revision`. Tests:
[`tests/README.md`](../tests/README.md).

How it works:

- **One checkpoint, by construction.** There is no downloaded "converted
  model". On the first start the decoder is converted from the checkpoint the
  service loaded and cached in the `ct2` volume under that file's SHA-256 (~2 s
  of conversion, ~6 s with the child process that does it). Every later start
  loads the cache.
- **The conversion runs in a child process.** In-process, the allocator kept
  the conversion's ~3 GB of fp32 scratch: 11.0 GiB resident against 8.0 GiB,
  and `malloc_trim` did not return it.
- **The conversion copies every tensor.** CTranslate2's int8 quantisation
  rescales the arrays it is handed in place, and for fp32 torch parameters
  those share memory with the model. Measured: |Δ| up to 127 on the token
  embedding, `conv1` and `fc1` until the converter cloned them.
- **Decoding options mirror `whisper.decode`.** Greedy, no timestamps, the
  `"-1"` non-speech set, blank suppression on the first step, at most 224 new
  tokens. CTranslate2's `max_length` counts double (it returns
  `max_length // 2` tokens), so the call passes 448.

| variable | default | |
|---|---|---|
| `NPU_STT_DECODER` | `torch` | `torch` or `ct2` |
| `NPU_STT_CT2_COMPUTE` | `int8` | any CPU compute type ctranslate2 offers: `int8`, `int8_float32`, `float32` |
| `NPU_STT_CT2_THREADS` | `8` | Measured in the service: 8 matches 16 on wall clock (142 vs 143 ms) at 40% less CPU (1.21 vs 2.00 s/request); 4 saves another 17% CPU for +43 ms |
| `NPU_STT_CT2_DIR` | `~/.cache/npu-whisper/ct2` | the `ct2` volume in `compose.yml` |

In the image, `WITH_CT2=1` puts `ctranslate2` and `PyYAML` into refenv from
`requirements/refenv-ct2.lock.txt` with `--no-deps`, because letting pip
resolve numpy replaces refenv's with one numba refuses to import. The build
then checks that refenv is exactly the lock files (see "Pinned versions" in
the top-level README).

## Language and context for clients that send neither

Some clients send neither `language` nor `audio_ctx`. voxtype's `remote` mode
is one: captured on the wire, it posts to `/v1/audio/transcriptions` with
`model=whisper-1`, `response_format=json` and **one** language. That is the
first entry of its `language` list, nothing at all for `"auto"`, or `auto`
with `remote_send_auto_language = true`. It never sends `audio_ctx`.

| variable | default | |
|---|---|---|
| `NPU_STT_LANG` | `en` (was `ru`) | Language for a request that names none. An absent language is **not** detection. |
| `NPU_STT_DETECT_LANGS` | empty (any) | `language=auto` (any case) detects on the first window's encoder output, among these codes (e.g. `pt,en`), and later windows reuse the result. It costs 15-35 ms, because the encoder output is already there. |
| `NPU_STT_CTX_FROM_AUDIO` | `0` | `1`: with no `audio_ctx`, size the context to the decoded audio (50 positions/s, +10% +16, onto the ladder; 1500 from 30 s) instead of `NPU_STT_DEFAULT_CTX`. Never below what the audio needs. |

Every response says what was used: `X-STT-Language`, `X-NPU-Ctx`,
`X-NPU-Ctx-Source` (`client` / `audio` / `default`) and `X-NPU-Detect-Ms`.
`/health` reports `default_language`, `detect_languages` and `ctx_from_audio`.

voxtype on this service (`~/.config/voxtype/config.toml`):

```toml
[whisper]
mode = "remote"
remote_endpoint = "http://127.0.0.1:8090"
remote_send_auto_language = true
language = "auto"         # with NPU_STT_DETECT_LANGS=pt,en on the service
```

Measured through voxtype itself (`voxtype -v transcribe`, its own "completed
in" times), against voxtype's local Vulkan backend on the Radeon 780M, with the
same pt/en switching on both sides. Ryzen 7 8700G, `large-v3-turbo`, ct2
decoder, a mixed sequence of 8 phrases:

| phrase | iGPU, pt/en detection | iGPU, language fixed | NPU, pt/en detection |
|---|---|---|---|
| 6 s pt, same length as the previous one | 2.55-2.60 s | 1.46 s | **1.35 s** |
| 6 s pt, after a phrase of another length | 2.55-2.60 s | 1.46 s | 2.21-2.23 s |
| 11 s en (`jfk.wav`) | 2.50-2.56 s | 1.46 s | 2.90 s |
| 20 s pt | 2.83-2.84 s | — | 4.26-4.29 s |
| the 8 phrases | 21.05 s | — | 21.52 s |

- **Language detection is what separates the two.** voxtype's local
  constrained detection costs ~1.1 s on the iGPU: it logs the detection 1.1 s
  after starting, then transcribes. Here detection rides on the encoder pass
  that transcription needs anyway.
- **Context switches cost ~0.6-0.85 s.** A request whose length falls in a
  different ladder step than the previous one re-uploads the geometry (encoder
  1.8 s instead of 1.2 s at ctx 512). Short phrases in a row stay at 1.35 s.
  (Before shared weights; a switch now costs 0.1-0.2 s, see below.)
- **Long phrases are still the iGPU's.** At 20 s the NPU encoder alone is
  ~3.1 s, plus the switch.
- voxtype does **not** fall back to its local backend when the service is
  down: the request fails with `Connection refused` and the dictation is lost.

### With the language fixed

The detection column above is not a like-for-like comparison: voxtype's
constrained detection (`language = ["pt", "en"]`) encodes the audio twice on
the iGPU (`select_language_from_allowed`, `src/transcribe/whisper.rs`), and the
service detects for free. Fixed to the clip's language on both sides
(`language = "pt"` or `"en"`, one temporary config per side), the iGPU wins
every case.

Measured through voxtype itself (`voxtype -c <config> -v transcribe <wav>`, its
own "completed in"), voxtype 1.1.1, `large-v3-turbo`, ct2 int8 decoder on the
service, 2026-10-17. Each case is the median of 4 runs (range in brackets).
"Warm" means the previous request was the same clip; "after a switch" means it
was a clip from a different ladder step. The iGPU loads its model in each
`transcribe` process (0.32-0.36 s, not counted); the daemon keeps it resident.

| phrase (ctx step on the NPU) | iGPU, fixed | NPU, fixed, warm | NPU, fixed, after a switch |
|---|---|---|---|
| 6 s pt (512) | 1.29 s (1.28-1.32) | 1.33 s (1.31-1.34) | 2.20 s (2.18-2.22) |
| 11 s en, `jfk.wav` (768) | 1.30 s (1.29-1.33) | 2.05 s (2.03-2.06) | 2.93 s (2.88-2.93) |
| 20 s pt (1280) | 1.56 s (1.55-1.57) | 3.40 s (3.36-3.44) | 4.22 s (4.20-4.24) |
| the 8 phrases, twice | 10.92 s, 10.89 s | — | 21.37 s, 21.29 s |

- The NPU's best case, short phrases back to back, ties the iGPU: 1.33 s
  against 1.29 s. Everything else is 1.6-2.7× slower.
- The iGPU's time barely depends on the phrase length: whisper.cpp encodes the
  full 30 s window (1500 positions) every time. The NPU's encoder alone
  (1.18 s at 512, 1.89 s at 768, 3.02 s at 1280, warm) costs about as much as
  the iGPU's whole transcription, before the 0.14-0.37 s CPU decoder.
- A switch between ladder steps costs another 0.8-0.9 s on the NPU. Since
  weights stay resident across ladder steps (see "Known limits"), it costs
  0.1-0.2 s: after a switch, 1.45 s (6 s), 2.30 s (11 s) and 3.64 s (20 s)
  through voxtype, against 1.34 / 2.13 / 3.48 s warm. The 8 phrases take
  17.4 s instead of 21.3 s, still well behind the iGPU's 10.9 s. The energy
  table below was measured before this change.
- Both sides produce the same text on all three clips: 0% WER on the 6 s and
  11 s clips, and 12.8% on the 20 s clip on both (digits for spelled-out numbers,
  and "8600G" for "oito mil e setecentos G").
- The 1.46 s figure in the table above was measured the same way earlier that
  day; this run gives 1.29-1.30 s. Every iGPU run here falls in 1.28-1.33 s
  (6 s and 11 s clips), so the earlier figure was probably taken under some
  other load.

On speed, then, there is no case for the NPU against the 780M. What is left to
argue is power and keeping the iGPU and the CPU free.

### Energy per transcription

Package energy from RAPL (`intel-rapl:0/energy_uj`, sampled every 20 ms as
root), with the machine otherwise idle, 2026-10-17. All three paths went
through voxtype 1.1.1 `transcribe` with the language fixed:

- NPU: the service, ct2 int8 decoder on the CPU;
- iGPU: `voxtype-vulkan`;
- CPU: `voxtype-avx512`.

Each request had a fixed slot of 15 s (25 s on the CPU), long enough to include
the tail after it. The figure is the marginal energy: the joules over the slot
minus the idle power over the same span. The iGPU and the CPU are counted from
voxtype's "Transcribing" log line, which leaves out their per-process model
load (3.6 J and 0.34 s each time; the daemon keeps the model resident). Each
case is the median of 4-8 requests (range in brackets), `large-v3-turbo`.

| phrase (ctx step) | NPU | iGPU | CPU |
|---|---|---|---|
| 6 s pt (512), same step as the previous one (n=5 NPU) | **29.8 J** (29.3-30.3), 1.45 s | 44.9 J (42.9-59.8), 1.29 s, all 8 | 691 J, 15.3 s |
| 6 s pt (512), after a switch (n=3) | 45.3 J (44.5-45.6), 2.27 s | (no switch cost) | — |
| 11 s en, `jfk.wav` (768), after a switch | 53.7 J (53.3-55.1), 3.04 s | 44.1 J (43.0-52.8), 1.29 s | 688 J, 15.3 s |
| 20 s pt (1280), after a switch | 78.7 J (76.0-86.7), 4.33 s | 51.7 J (51.3-52.8), 1.54 s | 699 J, 15.6 s |
| the 8 phrases | 400 J, 420 J | 385 J, 380 J | 5537 J |

| idle state (90 s each) | package |
|---|---|
| service stopped, voxtype daemon in remote mode | 4.42 W |
| service up, geometry resident | 4.67 W |
| service up + a second voxtype daemon with the Vulkan model resident | 4.84 W |

- **The NPU draws half the power but runs 2-3× longer.** During a request the
  socket (amdgpu PPT) sits at 19-21 W on the NPU path and at 40-41 W on the
  iGPU path. Energy per request comes out ahead only where the NPU is nearly
  as fast: short phrases on an unchanged geometry, 34% less than the iGPU.
  After a switch it ties. At 11 s and 20 s it costs 22% and 52% more. Over the
  mixed sequence the two are level.
- **About 10 J of every NPU request is the tail.** The NPU stays `active` for
  5.8 s after the response (median, 4.9-6.1 s), which is the driver's
  `autosuspend_delay_ms = 5000`, and the package sits ~1 W above idle in that
  window. The iGPU drops to its lowest sclk level as soon as it is done (0% of
  tail samples above level 0) and shows no tail. Without the tail, the NPU's
  request energy is 21.7 J against the iGPU's 47 J at 6 s warm, 43.8 J against 45.8 J
  at 11 s, and 67.8 J against 54.1 J at 20 s.
- **Resume from runtime suspend costs ~0.12 s of latency.** With 15 s between
  requests the NPU is suspended when each one arrives: a warm 6 s phrase takes
  1.45 s here against 1.33 s back to back. Real dictation has gaps, so 1.45 s
  is the realistic warm figure.
- **The CPU share of an NPU request is small.** 4-6% of all 16 threads is the
  ct2 decoder. The iGPU path uses 2%. The CPU-only path uses 25% for 15 s, at
  ~14× the energy: it is not a contender.
- **Idle cost is small and not resolved.** The resident service adds
  ~0.25 W (its Python process: 0.6% CPU against 0.4%; the NPU itself is
  suspended), and the resident Vulkan model adds ~0.17 W. Both are within the
  drift between phases taken minutes apart: the iGPU tail came out at −2.1 J
  against the same baseline.
- These figures come from a desktop APU (8700G). A battery claim needs the
  same measurement on a Phoenix/Hawk Point laptop.

In absolute terms, the best case saves ~16 J per short phrase (~0.004 Wh):
0.44 Wh a day at 100 dictations, at the cost of 0.16 s more latency.

## Known limits

- Every encoder pass uses **9 designs** (xclbins), but NPU1 holds only 6
  hw_contexts at once. Each warm pass therefore creates and evicts 7 contexts.
  This was measured in the service's own code (`load_backend` and `transcribe`,
  run in the service image), at every ladder step. The churn is cheap:
  `CREATE_HWCTX` takes 2.2-2.6 ms per warm pass in total, about 0.1-0.2% of the
  encoder. On the first pass after a geometry switch it takes 36-45 ms. The
  0.6-0.9 s that a switch costs is therefore weight re-upload, not context
  creation, and it is gone now: a weight BO is keyed by its padded layout
  (K, N, tiles), which does not depend on M, and a `host_only` BO is not tied
  to the hw_context it was allocated against. One upload (~1.26 GB of bf16
  for turbo, in system RAM, much like the Vulkan model's 1624 MB of GTT)
  serves every step and survives the switch teardown. The first pass after a
  switch is now 60-100 ms over warm, down from 0.6-0.9 s.
  Merging the designs into ≤6 xclbins would save the creation time,
  plus whatever the evicted designs make the next pass rebuild (operand BOs,
  attention-chain runlists). That rebuild time is inside the warm figures and
  is not isolated here. Designs and launches per pass at ctx 512: QKV/out GEMM
  288, fc1, fc2, GELU, QK, softmax and AV 32 each, the two convolutions and the
  embedding GEMM 1-2 each. The other steps use the same designs with M scaled.

- Speech longer than 30 s is windowed with a fixed stride, while `whisper.cpp`
  advances the window by timestamps. Text agrees inside a window and diverges at
  the seam.
- With the torch decoder, the decoder and not the encoder is the bottleneck:
  torch fp32 costs 2.4 s on a 22.6 s clip against 338 ms for whisper.cpp's
  quantised decoder — 42% of end-to-end. Threads do not help (the decode is
  latency-bound, 103 sequential steps); the wall is flat at 4/8/16. With
  `NPU_STT_DECODER=ct2` the encoder is the bottleneck again (see above).
- The process holds ~12.7 GB resident (weights plus the torch decoder); measured
  on an 8700G with `large-v3-turbo`, the container sits at 8.3 GiB with torch
  and 8.0 GiB with ct2.

## Units

`units/npu-stt.service` starts the `stt` service from the repo's `compose.yml`
at boot, which is the whole of it — compose publishes the port itself. It
expects the checkout in `/opt/npu-whisper` and `RENDER_GID` in
`/etc/default/npu-stt`; both are one line to change.
